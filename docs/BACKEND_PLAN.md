# ⚙️ پلن توسعه بک‌اند: ارتباط Go Super Node با لایه BFF

این سند نحوه آماده‌سازی بک‌اند Go (Super Node) را برای ارتباط با لایه BFF (Bun) شرح می‌دهد.

## ۱. معماری ارتباطی (Go و BFF)
در معماری نهایی سیستم ما، **فرانت‌اند (SvelteKit) هرگز به طور مستقیم با Go Super Node ارتباط برقرار نمی‌کند.** تمام ارتباطات استریمینگ و AI توسط لایه **BFF (Bun)** با استفاده از Vercel AI SDK هندل می‌شود. 

بنابراین، برخلاف معماری‌های قدیمی که نیازمند پیاده‌سازی دستی Vercel Data Stream Protocol در Go بودیم، اکنون Go صرفاً به عنوان یک **موتور اجرای منطق (Logic Engine)** عمل می‌کند.

## ۲. نقش بک‌اند Go در چرخه هوش مصنوعی
وظیفه Go دریافت دستورات (Tool Calls) از سمت BFF، اجرای آن‌ها و برگرداندن نتیجه به BFF است.

### گام ۱: دریافت درخواست اجرای ابزار (Tool Call) از BFF
هنگامی که LLM (از طریق Bun) تشخیص دهد که باید ابزاری اجرا شود (مثلا `deploy_website`)، سرور Bun یک درخواست `POST` استاندارد (REST یا gRPC) به سرور Go می‌فرستد.

فرمت درخواستی که Go از Bun دریافت می‌کند (نمونه REST):
```json
{
  "tool_name": "deploy_website",
  "tool_args": {
    "project_name": "test_project",
    "template": "react"
  },
  "context": {
    "user_id": "usr_123"
  }
}
```

### گام ۲: اجرای منطق (Temporal / Rivet / Wasm)
بک‌اند Go بر اساس `tool_name` درخواست را به یکی از بخش‌های زیر هدایت می‌کند:
1.  **Temporal:** برای ورک‌فلوهای طولانی‌مدت و مقاوم در برابر خطا.
2.  **Rivet Service:** برای اجرای گراف‌های منطقی بصری.
3.  **Wazero (TinyGo):** برای اجرای سریع منطق‌های ایزوله در لبه.

### گام ۳: بازگرداندن نتیجه به BFF
پس از اتمام (یا در حین اجرای) وظیفه، Go نتیجه را با یک فرمت استاندارد JSON به Bun برمی‌گرداند. نیازی به فرمت‌های پیچیده استریمینگ (مثل پیشوند `a:`) در Go نیست.

فرمت پاسخی که Go به Bun می‌دهد:
```json
{
  "status": "success",
  "result": {
    "url": "https://test-project.dpin.network",
    "deployment_id": "dep_456"
  }
}
```
پس از دریافت این پاسخ، **سرور Bun (BFF)** وظیفه دارد این نتیجه را با فرمت استاندارد Vercel AI به فرانت‌اند استریم کند.

## ۳. معماری پیشنهادی در Go (Super Node)

1.  **Internal API Gateway:** روت‌های داخلی (مثلاً `POST /internal/tools/execute`) که فقط از سمت Bun (BFF) قابل دسترسی هستند.
2.  **Tool Registry:** یک رجیستری مرکزی در Go که مشخص می‌کند هر `tool_name` باید توسط کدام سرویس (Temporal، Rivet یا Wasm) اجرا شود.
3.  **Event Publisher (Redpanda):** در صورتی که ابزار اجرا شده تغییری در وضعیت سیستم ایجاد کند (مثلاً آپدیت دیتابیس)، Go یک رویداد در Redpanda منتشر می‌کند تا بقیه سیستم مطلع شوند.

## ۴. فازهای توسعه بک‌اند (بخش Go)
1. **فاز اول:** ایجاد روت داخلی `/internal/tools/execute` و پیاده‌سازی یک `Mock Tool` که یک پاسخ JSON ثابت برمی‌گرداند.
2. **فاز دوم:** اتصال رجیستری ابزارها به Temporal برای اجرای ورک‌فلوهای واقعی.
3. **فاز سوم:** اتصال به `Rivet Service` از طریق gRPC برای اجرای گراف‌های منطقی پیچیده عامل‌ها.
